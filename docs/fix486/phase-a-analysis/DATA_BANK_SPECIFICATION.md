# FIX486 hierarchical data bank specification

## 1. Bank identity

```text
BANK_ID=fix486-hierarchical-bank
BANK_VERSION=0.1.0-analysis-seed
BANK_STATUS=SEED_FOR_ANALYSIS
```

Version `0.1.0-analysis-seed` is not yet an immutable final quality bank. Codex must analyze its feasibility against the actual AstraVector identity model and publish a proposed `1.0.0` bank in Phase 1.

## 2. Goals

The bank must support objective proof of:

- multi-granularity ingestion;
- deterministic hierarchy identity;
- child-to-parent retrieval;
- parent grouping and deduplication;
- exact technical child evidence;
- access-zone isolation;
- version/lifecycle filtering;
- stale Qdrant and orphan-child handling;
- Graph-expanded child parent resolution;
- MMR diversity;
- token-budget required-intent protection;
- large-parent budget pressure.

## 4. Required identities

The bank describes logical identities, not assumed database primary-key mechanics. Codex must map logical IDs to the actual deterministic IDs generated by AstraVector.

Required logical identifiers:

```text
zone-a
zone-b
doc-hierarchy
source-a
parent-a1
parent-a2
parent-a3
parent-large
child-a1-180
child-a1-260
child-a2-180
child-a2-260
child-a3-180
child-a3-260
child-large-180
```

For deliberate cross-zone collision, both zones use the same logical document, parent and child labels but different content. If the actual Qdrant point identity cannot safely be duplicated, the fixture must preserve equal logical chunk identity while using the production zone-scoped point identity.

## 5. Document content principles

Each expected child must contain a unique anchor that is not present in distractors. Examples:

```text
ASTRA_CANONICAL_STATE_A1
ASTRA_LEGAL_HOLD_A2
ASTRA_RECONCILIATION_A3
ORA-00904
content_chunks_v004
/api/v1/search
```

The parent must contain enough surrounding context to prove that `parent_text` is broader than `matched_text`.

Expected labels must not be generated from runtime output.

## 6. Lifecycle variants

The same logical document must have controlled versions:

```text
version 1 ACTIVE
version 2 INDEXING/INACTIVE with a higher lexical attraction
version 3 DELETED
version 4 EXPIRED
version 5 ACTIVE with legal hold where applicable
```

The bank must distinguish expected absence because of lifecycle from absence because retrieval failed.

## 7. Graph fixture

Required relation:

```text
child-a1-180 --REPAIRED_BY--> child-a3-180
```

Direct retrieval should seed A1. Graph expansion should discover A3 and hydrate `parent-a3`, never reuse `parent-a1` for the Graph child.

## 8. Multi-intent fixture

Required intents:

```text
A: PostgreSQL canonical state
B: legal hold and TTL
C: Qdrant missing-point reconciliation
```

The bank must support:

- all three intents covered;
- only A covered;
- A and C covered through direct + Graph;
- B as the only lower-score context;
- constrained token budget where dropping B would create false full coverage.

## 9. Large-parent pressure fixture

```text
parent-large: approximately 900 canonical tokens, high score, covers only A
parent-a2: approximately 250 canonical tokens, covers B
parent-a3: approximately 250 canonical tokens, covers C
```

Exact token counts must be generated with the configured tokenizer in Phase 1. The seed bank records target ranges only.

## 10. Bank mutation policy

After a `1.0.0` manifest is frozen:

- queries and qrels cannot be silently edited;
- expected IDs cannot be changed to match runtime output;
- fixture corrections require a new version;
- every new version must state which prior evidence runs are invalidated;
- production fixes and bank changes must be separate commits.

## 11. Acceptance for Phase A

The seed bank is acceptable when Codex confirms:

```text
BANK_SCHEMA_VALID
FIXTURE_FEASIBLE_WITH_PRODUCTION_IDENTITY
NO_EXPECTATION_DEPENDS_ON_RUNTIME_OUTPUT
ALL_TEN_CASES_HAVE_QUERY_AND_QREL
LIFECYCLE_STATES_REPRODUCIBLE
GRAPH_RELATION_REPRODUCIBLE
PHASE_1_FREEZE_PLAN_DEFINED
```

If any condition is impossible, the analysis verdict must be `FIX486_ANALYSIS_BLOCKED` with a concrete redesign proposal.
